`$ARGUMENTS` 기능을 **만들거나 고친다**. 사용자는 이 명령 하나만 알면 된다 — 무엇을 할지는 아래 순서로 스스로 고른다.
다른 명령 파일은 `${CLAUDE_PLUGIN_ROOT}/commands/`에서 읽어 그 절차를 따른다 (사용자에게 다른 명령을 부르라고 시키지 않는다).

## 0. 하네스가 안 켜져 있으면 먼저 켠다

`.claude/harness.conf`가 없으면 `harness-init` 스킬(`${CLAUDE_PLUGIN_ROOT}/skills/harness-init/SKILL.md`)의 "켜기" 절차로 켠다 (질문 없이 자동 진단 → conf 생성 → check 확인). 한 줄로 알리고 이어서 진행한다.
check가 지금 실패하면 **멈추고** 실패 목록을 보여준 뒤 먼저 고칠지 묻는다 — 깨진 바닥 위에서 기능을 쌓지 않는다.

## 1. 대상 문서 정하기

- `$ARGUMENTS`가 비어 있으면: `bash "${CLAUDE_PLUGIN_ROOT}/scripts/spec-status.sh" --brief`. 바뀐 문서가 있으면 그 문서들을 차례로 처리하고, 없으면 무엇을 만들지 묻는다.
- 기능 이름이면 문서는 `<SPECS_DIR>/<이름>.md` (기본 `docs/specs`).
- 문서 경로인데 `SPECS_DIR` **밖**이면 (예: 루트의 `계산기.md`): `SPECS_DIR/<파일이름>`으로 **옮기고** 한 줄로 알린다. 다른 파일이 원래 경로를 참조하고 있으면 옮기지 말고 복사한다.

## 2. 상태 보고 할 일 고르기

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/spec-status.sh" --state <이름>
```

| 상태 | 뜻 | 할 일 |
| --- | --- | --- |
| `missing` | 문서 없음 | `spec.md` 절차로 초안 → **확인 1회** → `new`로 |
| `freeform` | 문서는 있지만 규칙 줄(`- R1 …`)이 없음 — 사용자가 자유롭게 쓴 글 | 아래 "자유 문서 → 규칙" → **확인 1회** → `new`로 |
| `new` | 규칙은 있고 아직 만든 적 없음 | `check-feature.md` 절차 (처음부터) |
| `changed` | 만든 뒤 문서가 바뀜 | `sync.md` 절차 (바뀐 규칙만) |
| `synced` | 문서대로 이미 반영됨 | "이미 문서대로예요"라고 알리고, 보고서가 없으면 만든다. 끝. |

### 자유 문서 → 규칙

사용자가 쓴 글은 **지우지 않는다.** 글은 그대로 두고 맨 아래에 `## 규칙` 절을 붙인다.

- 글에서 읽히는 동작을 `spec.md` 형식의 규칙 줄로 옮긴다 (한 줄 하나, 번호 R1부터, 실패·경계 상황 포함).
- 글에 없는데 필요해 보이는 규칙(예: 0으로 나누기, 빈 입력)은 넣되 `(확인 필요)`를 붙인다.
- 사용자에게 **규칙 목록과 확인할 질문을 한 번에** 보여주고 답을 받는다 (AskUserQuestion은 확인 필요 항목이 있을 때만, 최대 4개). 답에 맞춰 문서를 고친 뒤 진행한다.
- 답을 받을 수 없는 상황(비대화형 실행 등)이면 `(확인 필요)` 규칙은 **만들지 않고** 나머지만 진행한 뒤, 보고의 "사람이 확인할 것"에 올린다.

## 3. 확인 강도 고르기 — 빠름 / 꼼꼼

이번에 다룰 규칙(새 기능이면 전체, 고치기면 바뀐 규칙만)을 보고 고른다. 우선순위:

1. 사용자가 말로 정했으면 그대로: "빠르게" → 빠름, "꼼꼼하게" / "제대로" → 꼼꼼.
2. `.claude/harness.conf`의 `MODE`가 `fast` → 빠름, `full` → 꼼꼼.
3. `MODE=auto`(기본, 없어도 auto)면:
   - **꼼꼼**: 처음 만드는 기능(`missing` · `freeform` · `new`) / 다룰 규칙이 6개 이상 / **위험한 영역**이 하나라도 있음
   - **빠름**: 그 밖의 작은 수정 (바뀐 규칙 5개 이하, 위험한 영역 없음)

**위험한 영역** = 로그인·권한·소유권 · 결제·금액 · 데이터 저장·삭제·이전 · 보안·개인정보 · 외부로 나가는 요청(메일·알림·외부 API 쓰기).

| | 꼼꼼 | 빠름 |
| --- | --- | --- |
| 규칙마다 테스트 먼저 → 실패 확인 → 구현 → 통과 | ✅ | ✅ (실패 확인·통과는 규칙별로 따로 돌리지 말고 한 번에 모아 돌린다) |
| 일부러 망가뜨려 보기 | 규칙마다 | **실패·오류 처리 · 경계값 · 위험한 영역 규칙만**. 그런 규칙이 없으면 가장 핵심인 규칙 1개 |
| check 통과 | ✅ | ✅ |
| 화면 확인 | 최대 3회 | 1회 |
| 독립 검사 (verifier) | ✅ | **생략** — 대신 끝에 문서 규칙 목록을 다시 읽고, 규칙마다 그 번호가 붙은 테스트가 있는지 직접 대조한다 |
| 보고서 | ✅ | ✅ |
| 데모 영상 | 조건 맞으면 자동 | 사용자가 요청할 때만 |

시작할 때 일지에 남긴다: `bash "${CLAUDE_PLUGIN_ROOT}/scripts/journal.sh" <이름> mode - "빠름"` (또는 `"꼼꼼"`). 보고서가 무엇을 생략했는지 직접 밝힌다.
진행 중 위험한 영역이 드러나면(예: 고치다 보니 저장 로직을 건드림) 그 자리에서 꼼꼼으로 올리고 일지에 `mode - "꼼꼼"`을 다시 남긴다. 빠름으로 내리지는 않는다.

## 4. 만들기 / 고치기

고른 절차(`check-feature.md` 또는 `sync.md`)를 끝까지 따르되, **3에서 고른 확인 강도가 그 절차의 망가뜨려 보기·화면 확인·독립 검사 횟수보다 우선한다.**
공통 순서: 규칙별 테스트 먼저 → 실패 확인 → 구현 → 통과 → 일부러 망가뜨려 보기 → check 통과 → 화면 확인(화면 있으면) → 독립 검사(꼼꼼일 때) → 모두 ✅면 반영 완료 표시 → 일지 기록.

규칙 하나가 3번 고쳐도 안 되면 그 규칙은 ❌로 두고 나머지를 계속한다. 붙잡고 멈춰 있지 않는다.

## 5. 결과물 (묻지 않고 만든다)

1. 제작 과정 보고서: `node "${CLAUDE_PLUGIN_ROOT}/scripts/report.mjs" <이름>`
2. 데모 영상 (꼼꼼일 때): 화면 있는 기능이고 **Playwright 설정 + 규칙 번호가 붙은 E2E**가 있으면 `demo.md` 절차로 만들고 보고서를 다시 만든다. 없으면 건너뛰고 마지막 보고에 "영상: E2E가 없어 건너뜀" 한 줄. 빠름일 때는 "영상이 필요하면 말씀해 주세요" 한 줄.

## 6. 마지막 보고

`harness-report` 형식을 쓰되, **사용자에게는 하네스 내부 용어를 쓰지 않는다.**
판정 바로 아래에 **확인 강도와 그 이유를 한 줄**로 적는다. 빠름이면 무엇을 생략했는지와 꼼꼼하게 다시 하는 방법도 같은 줄에.

| 쓰지 말 것 | 대신 |
| --- | --- |
| verifier, 서브에이전트 | 독립 검사 |
| mutation, 뮤턴트 | 일부러 망가뜨려 봄 |
| sync, 스냅샷, 반영 완료 표시 | "문서대로 반영됨" (또는 말하지 않음) |
| Stop 훅, fingerprint | 자동 검사 |
| N단계 | (말하지 않음) |

## 지켜야 할 것

- 문서에 없는 동작을 코드에만 추가하지 않는다. 요청이 문서에 없으면 문서에 먼저 규칙으로 넣고(확인받고) 만든다.
- 테스트 기대값을 바꿔 통과시키지 않는다 (규칙이 바뀐 `~수정`만 예외).
- 커밋·푸시는 사용자가 요청할 때만.
