`docs/specs/$ARGUMENTS.md`의 **규칙마다 테스트 하나**를 만든다. 문서가 없으면 멈추고 `/harness-init:spec $ARGUMENTS`를 먼저 하라고 안내한다.

## 1. 테스트 작성

- 테스트 이름에 규칙 번호를 넣는다: `R3: 이미 있는 이메일이면 안내 문구를 보여준다`.
- 프로젝트가 이미 쓰는 테스트 도구·위치·스타일을 따른다.
  - 웹 화면 → E2E (Playwright, Cypress)
  - API 서버 → HTTP 요청 테스트 (supertest, httpx 등)
  - 순수 로직 → 단위 테스트
- 문서에 없는 동작은 테스트로 만들지 않는다. 필요해 보이면 "문서에 추가할 규칙 후보"로 따로 적는다.

### 모킹 원칙

| 요청 종류 | 어떻게 |
| --- | --- |
| 읽기 | 가능하면 진짜로 (개발 서버, 로컬 DB) |
| 쓰기 · 삭제 | 가짜로 가로채되, **무엇을 보냈는지**(URL·본문)는 검사 |
| 운영 서버 | 절대 연결하지 않음 |

## 2. 통과시키기

- 테스트를 돌려 통과시킨다. 실패하면 **기능 코드를 고친다.** 규칙과 다른 테스트 기대값을 슬쩍 바꿔 통과시키지 않는다.
- 규칙 자체가 틀려 보이면 고치지 말고 사용자에게 묻는다.

## 3. 일부러 망가뜨려 보기 (반드시)

규칙마다:
1. 그 규칙을 담당하는 기능 코드 한 곳을 Edit로 망가뜨린다 (조건 뒤집기, 한 줄 삭제, 반환값 바꾸기).
2. 해당 테스트만 돌린다 → **실패해야 정상.**
3. Edit로 원래대로 되돌린다. (`git checkout`/`git stash`로 되돌리지 않는다 — 다른 미커밋 작업을 날릴 수 있다.)
4. 망가뜨려도 통과하면 그 테스트는 아무것도 검사하지 않는 것이다 → 테스트를 고친다.

끝나고 `git diff`로 망가뜨린 흔적이 남지 않았는지 확인한다.

## 4. 보고

`harness-report` 스킬의 형식으로, 규칙별로 테스트 이름·통과 여부·망가뜨려 보기 결과(실패함 ✅ / 그래도 통과 ❌)·확인 깊이를 적는다.

## 일지 남기기 (제작 과정 보고서 재료)

단계마다 한 줄씩 기록한다. 기능 이름은 문서 이름과 같게.

```bash
J="${CLAUDE_PLUGIN_ROOT}/scripts/journal.sh"
bash "$J" <기능> test R3 "tests/calc.test.ts › R3 곱셈 우선"     # 테스트 작성
bash "$J" <기능> red R3 "expected 14, received 20"               # 먼저 실패 확인
bash "$J" <기능> impl R3 "src/calc.ts — 우선순위 파서"            # 구현
bash "$J" <기능> green R3                                        # 통과
bash "$J" <기능> mutant-killed R3 "우선순위 표를 같게 → 실패함"   # 망가뜨려 보기 (잡음)
bash "$J" <기능> mutant-survived R3 "…를 바꿔도 통과"             # 망가뜨려 보기 (못 잡음) → 테스트 고친 뒤 fix·mutant-killed 기록
```

`red`를 건너뛰지 않는다 — 먼저 실패하는 걸 봐야 테스트가 뭔가를 검사한다는 증거가 된다.
