규칙 문서를 **마지막으로 반영한 스냅샷**과 비교해, 바뀐 규칙만 코드에 반영한다.

## 1. 무엇이 바뀌었나

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/spec-status.sh" $ARGUMENTS
```

- 출력이 없으면 "반영할 변경 없음"이라고 말하고 끝낸다.
- 출력을 표로 보여준다: 문서 · 규칙 · 종류(추가/수정/삭제) · 내용.
- 새 문서(아직 반영한 적 없음)인데 이미 구현·테스트가 있는 기능이면, 전부 새로 만들지 말고 **기존 테스트로 규칙이 덮이는지 먼저 확인**한다. 이미 다 덮이면 사용자에게 묻고 반영 완료로만 표시한다.

## 2. 멈추고 물어볼 것 (AskUserQuestion, 한 번에 모아서)

- **삭제된 규칙**: 해당 테스트와 기능 코드를 지울지 (지우지 않고 남겨 두는 선택지도 준다).
- **`(확인 필요)`가 붙은 규칙**: 확정됐는지.
- 규칙끼리 **충돌**하거나 기존 규칙과 모순되는 경우.
- 문서가 삭제된 경우: 그 기능의 테스트·코드를 정리할지.

추가·수정 규칙이 명확하면 묻지 않고 진행한다.

## 3. 규칙별로 반영

규칙 번호 순서대로. 각 규칙은 `rule-tests` 명령(`${CLAUDE_PLUGIN_ROOT}/commands/rule-tests.md`)의 절차를 따른다.

| 종류 | 할 일 |
| --- | --- |
| **+ 추가** | 테스트 먼저(이름에 규칙 번호) → 실패 확인 → 기능 구현 → 통과 → 망가뜨려 보기 |
| **~ 수정** | 그 규칙 번호의 기존 테스트를 찾아 **새 규칙에 맞게** 기대값을 고친다 → 실패 확인 → 기능 코드 수정 → 통과 → 망가뜨려 보기. 규칙이 바뀌었으니 테스트 수정은 정당하다 — 보고에 "R7 규칙 변경에 따라 기대값 수정"이라고 적는다 |
| **- 삭제** | 2단계에서 승인받은 경우에만 테스트·코드를 지운다. 다른 규칙 테스트가 깨지지 않는지 확인 |

- 바뀌지 않은 규칙의 테스트는 건드리지 않는다. 깨지면 그건 회귀다 — 기능 코드를 고친다.
- 화면에 영향이 있는 변경이면 `visual` 절차로 캡처 확인 (최대 3회).

## 4. 검증

1. 프로젝트 check(`.claude/harness.conf`의 `CHECK_CMD`)가 통과해야 한다.
2. **verifier 서브에이전트**에게 문서 경로와 "이번에 바뀐 규칙 번호 목록"만 넘겨 검사시킨다 (구현 설명은 넘기지 않는다).

## 5. 반영 완료 표시

바뀐 규칙이 **모두 ✅**인 문서만 표시한다. 하나라도 ❌·미확인이면 표시하지 않는다 (다음에 다시 sync 대상).

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/spec-status.sh" --mark <기능이름>
```

스냅샷(`.claude/harness-synced/`)은 코드 변경과 **같은 커밋**에 넣으라고 안내한다 — 그래야 다른 컴퓨터에서도 "어디까지 반영됐는지"가 맞는다.

## 6. 보고

`harness-report` 형식. 판정 첫 줄 아래에 **이번 sync 범위**를 적는다:

```
판정: ✅ 통과
이번 sync: calculator — +R10 ~R7 -R3
- R10 ✅ 화면까지 (새 테스트)
- R7 ✅ 단위 테스트까지 (규칙 변경에 따라 기대값 수정)
- R3 ✅ 테스트·코드 삭제 (사용자 승인)
반영 완료 표시: calculator
```

## 일지 · 보고서

- 시작할 때 `journal.sh <기능> spec - "sync: +R10 ~R7 -R3"`, 규칙별 단계는 `rule-tests`의 일지 규칙대로 기록한다.
- verifier 결과는 규칙마다 `verify R7 "✅ 단위 테스트까지"`, 사람 확인은 `todo`, 마지막에 `verdict`로 기록한다.
- 끝나면 `node "${CLAUDE_PLUGIN_ROOT}/scripts/report.mjs" <기능>`로 제작 과정 보고서를 만들고 경로를 알려준다.
